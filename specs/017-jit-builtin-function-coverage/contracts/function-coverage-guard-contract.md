# Contract: `FUNCTION_`-mnemonic coverage guard (FR-010)

This extends, and is a sibling to, spec 011's existing `OPCODE_`-only
coverage-guard contract (`specs/011-jit-opcode-parity/contracts/coverage-guard-contract.md`)
— read that first; this document only covers what's new/different for the
`FUNCTION_` (builtin-function) family this feature adds.

## Where it runs

A `ctest` target under the existing `-L libshader` label, inside/alongside
the existing `test_opcode_coverage.cpp` (`src/libshader/tests/`). MUST NOT
be invoked from any render-time code path — same hard requirement as
spec 011's guard.

## Inputs (re-derived at test-run time, never a frozen list)

1. **Reachable set**: `kAllFunctionMnemonics[]` (new, `llvmEmitter.h`/`.cpp`)
   — generated by the same `#include`-based X-macro technique
   `kOpcodeParamTable` already uses (`llvmEmitter.cpp:156-177`), applied to
   only `scriptFunctions.h`'s `#include` chain (→ `shaderFunctions.h` →
   `giFunctions.h`), capturing each `DEFFUNC`/`DEFLINKFUNC`/
   `DEFLIGHTFUNC`/`DEFSHORTFUNC` entry's `text` field. The two `"XXX"`
   DSO-placeholder rows (`research.md` D7) are hand-excluded from this set
   — they are not real callable mnemonics and would otherwise be a
   permanent false-positive gap this guard could never close.
2. **Handled set**: `kHandledOpcodes[]` — the SAME table spec 011's guard
   already reads, read directly (not re-parsed from source text), so
   neither guard can ever drift from what the emitter actually dispatches
   on. `kHandledOpcodes[]` is a single, shared table across both the
   `OPCODE_` guard and this `FUNCTION_` guard — there is exactly one gate,
   one handled-set, checked by two reachable-set enumerations (bytecode
   operators vs. builtin functions).

Both sets are computed fresh on every test run. A builtin function added
to `scriptFunctions.h`/`giFunctions.h` after this feature ships, but never
added to `kHandledOpcodes[]`, fails this test without any manual update to
the test itself — this is what closes the exact structural gap that let
`random()`/`urandom()` (issue #1) and this feature's 25 functions ship
silently: `test_opcode_coverage.cpp`'s pre-this-feature guard could not see
`FUNCTION_`-family mnemonics at all.

## Pass/fail contract

- **Pass**: `kAllFunctionMnemonics` (minus `"XXX"`'s two rows) ⊆
  `kHandledOpcodes`.
- **Fail**: at least one member of `kAllFunctionMnemonics` (minus `"XXX"`)
  is not in `kHandledOpcodes`. The failure message MUST name the specific
  missing mnemonic(s) — e.g. `"JIT coverage gap: builtin function
  'visibility' is reachable but has no emitFunction() case"` — mirroring
  spec 011's message-format precedent. A bare count without names does not
  satisfy this contract.

## Supersession of issue #1's stopgap check

Issue #1's fix added a narrow, hand-written check in
`test_opcode_coverage.cpp` asserting only `"random"`/`"urandom"` are in
`kHandledOpcodes[]`, with a comment explicitly flagging it as a stopgap
pending "the follow-up GitHub issue for extending this guard to the full
FUNCTION_ mnemonic set." This feature's guard supersedes and subsumes that
check entirely — the hand-written `random`/`urandom`-only test SHOULD be
removed as part of implementing this guard (it becomes redundant: any
regression it would have caught, the general `kAllFunctionMnemonics`-based
guard now also catches, plus every other builtin function).

## Non-goals

- Does not check *correctness* of a handled function's codegen (that's the
  `-L visual` image-diff regression tests' job — the per-function probe
  pairs this feature's FR-018 requires, plus `quadlight`/`spherelight`'s
  FR-019 pair).
- Does not run at build/compile time — this is the test-suite-time half of
  this feature's two-layer defense (see `gate-hardening-contract.md` for
  the build-time half). A reachable-but-unhandled builtin function, before
  US2's gate-hardening lands, still compiles silently; after US2 lands, it
  fails to compile at all (caught earlier, by `oshader --jit` itself) —
  this guard remains valuable as an independent, additional check
  regardless (e.g. it also catches a case where the gate itself is
  mis-implemented in a way that lets an unhandled mnemonic slip through).
