## Dependencies and execution order

### Phase dependencies

- **Phase 0** (baselines) needs nothing and edits no code; every later phase compares with its numbers. `build-base` (T004) must exist before any `src/` edit.
- **Phase 1** (harness, red tests) needs Phase 0's pause answered. T030 (TEST-APPROVAL) precedes T031 (applying patches) and T033 (red evidence).
- **Phase 2** (photon map, US1) needs Phase 1. It is independent of every cache task and is the **MVP**: it fixes #163, #164 and #165 and unblocks `Registry_IntegratorImageIdentity`.
- **Phase 3** (lookup, D2) needs Phase 2 (the canonical map; the lookup tests use the byte-level helpers).
- **Phase 4** (sampler and accept) is independent of Phases 2 and 3 in code and may run after them or before them; it is placed after so that the photon work lands first. It must precede Phase 5: the final `lookupCached` signature lands here.
- **Phase 5** (cache, M2) needs Phase 4. **Phase 6** (`-P:N`) needs Phase 5 (`commitPending`, `forEachPending`).
- **Phase 7** (pins, references, overhead) needs Phases 2 to 6: the re-render is one step after every image-changing phase. T091 (photon pins) needs only Phase 2 and may be run earlier.
- **Phase 8** needs Phase 7 and D5's answer.

### Within a phase

- Red tests (the TEST-APPROVAL task, the tests) before the code that makes them green; the tests move out of the red block in the phase that satisfies them.
- A TEST-APPROVAL or REFERENCE-APPROVAL task stops the work: later tasks of the phase wait for the answer.
- Every checkpoint ends with `ctest -L architecture`, `git add` of explicit paths, a `validation.md` record and a PAUSE.

### Parallel opportunities

- `[P]` tasks within a phase touch different files and may be written together: T007 and T012 and T016 (Phase 0); T021, T022, T023, T024, T025, T026 and T029's tool (Phase 1: each writes its own new file); T037 (`map.h`) with the interface edits of T039 once T038's signatures are agreed (Phase 2); T056 with T058 (Phase 4); T100 to T103 (documents, Phase 8).
- `[RUN]` jobs are never parallel: one `cpujob` at a time machine-wide. The Linux jobs run on the remote's own lock and may overlap a macOS job only if the coordinator says so.

## Implementation strategy

1. **MVP**: Phases 0 to 2. A photon map is the same on every run and at every thread count, with no crash; the photon rows of `Registry_IntegratorImageIdentity` pass. This is shippable on its own and answers #163, #164 and #165.
2. **Then** Phase 3 (the lookup is pure, #160) and Phase 4 (a miss makes the same record whatever the cache held), which are small and independent.
3. **Then** Phases 5 and 6, the irradiance cache and `-P:N`. Their risk is image quality at batch boundaries (research.md R4): the quality gate (T074) goes to the maintainer before the Phase 7 re-render.
4. **Then** Phase 7 (one re-render, the pins, the overhead) and Phase 8 (documentation and the closing validation on both platforms).
