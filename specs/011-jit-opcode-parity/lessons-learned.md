# Lessons Learned — 011-jit-opcode-parity

Retrospective across the full branch (Phases 0-7), covering confirmed
defects, near-misses, and unexpected code/process surprises. Written
2026-08-21 per explicit user request, alongside the corresponding updates to
`spec.md` (FR-009 amendment), `CLAUDE.md`, and `DEVNOTES_DETAILS/BUGS.md` /
`OSHADER_UPDATES.md`.

## 1. Stale `.slo` bitcode is a silent-invalidation trap — and it's bigger than the known deploy-tree gotcha

**What happened**: During Phase 7 (US3b, `gather()`) verification,
`Visual_sphere-gather-reyes-slo` crashed with `EXC_BAD_ACCESS` in
`jitGatherHeaderBegin`, with garbage stride arguments (e.g.
`strideP=-1706065808`). The actual T037/T038 stride-threading logic in
`llvmEmitter.cpp` was correct. The crash's real cause was that
`shaders/gather_named_probe.slo` — a precompiled bitcode artifact — had been
generated by an `oshader` binary built *before* the stride-threading fix
landed. The runtime C++ side (`op_gatherHeader`/`jitGatherHeaderBegin`) had
already moved to the new 12-argument signature; the stale bitcode's call
site still emitted the old argument list, so the new parameters read
uninitialized stack/register contents instead of failing to link or
compile — nothing catches an ABI mismatch across a stale-bitcode-to-fresh-C++
boundary at build time.

Worse: fixing that one `.slo` and getting a green run was **not sufficient**.
A `stat` audit of all 10 `-slo`-suffixed test shaders found **9 of the other
10** (`array_ops_probe`, `show_st_hsv`, `comparison_logic_probe`,
`show_ctransform`, `matrix_ops_probe`, `blue_marble`, `brushedmetal`,
`somewood`, `wood`) were also 2 days stale relative to both the
`llvmEmitter.cpp` edit and the `oshader` rebuild — meaning an "87/87 visual
tests passing" result reported earlier in this branch's work was not
actually validating current emitter code for those 9 shaders. They happened
to still produce visually-passing output by coincidence (their code paths
weren't touched by the specific edits that went stale), not because the
staleness was harmless in general.

**Why this matters beyond this branch**: `CLAUDE.md` already documented this
gotcha, but scoped it to the *gitignored, `cmake --install`-only* deploy tree
(`openrender/shaders/*.slo`). This branch confirms the same silent-staleness
failure mode also applies to the **tracked** `shaders/*.slo` source-tree
copies that visual tests compile against directly — nothing in the build
graph regenerates `.slo` bitcode when `llvmEmitter.cpp` (or any oshader
source) changes, in *either* location. `CLAUDE.md` gotcha #3 needs to state
this generalized rule, not just the deploy-tree instance of it.

**Operational rule going forward**: after any change to
`src/libshader/compiler/*` (the `oshader --jit` pipeline), before trusting
any `-slo`-suffixed test result, `stat` every `.slo` file the test suite
depends on against the source file(s) that changed. If any `.slo` predates
the source change, rebuild `oshader` first (`cmake --build --target
oshader`), then regenerate every stale `.slo` via `oshader --jit -o <name>.slo
<name>.sl`, and refresh both the tracked `shaders/` copy and the deploy-tree
`openrender/shaders/` copy. Do not trust a green visual-test run as evidence
a JIT-emitter change is correct unless this check was done first.

## 2. `oshader -I <path>` combined with `-o` and a positional input fails to parse

**What happened**: regenerating `brushedmetal.slo`/`somewood.slo` (which
`#include` `.slh` headers from `shaders/includes/`) via
`oshader -I shaders/includes --jit -o shaders/<name>.slo shaders/<name>.sl`
failed with `Output file specified with multiple input files... Named output
file requires single input file` — despite there being exactly one `.sl`
positional argument. This is a CLI argument-parsing quirk/defect in
`oshader`'s option handling, not a real "multiple inputs" condition.

**Workaround** (confirmed working, and it's the documented mechanism per
`oshader --help`): use the `SHADERS_INCLUDE` environment variable instead of
`-I`:
```
SHADERS_INCLUDE="$(pwd)/shaders/includes" build/src/oshader/oshader --jit -o shaders/<name>.slo shaders/<name>.sl
```

This was not investigated further to root-cause the `-I` parsing bug itself
(out of this branch's scope), but it's worth a dedicated small fix at some
point since `-I` is the more discoverable/conventional flag name and its
current failure mode gives a misleading error message.

## 3. A raw opcode-list diff is not a trustworthy coverage check — compute the reachable set, don't hand-maintain it

**What happened** (Phase 4/T013): the original coverage-guard design
compared `opcodes.cpp`'s full mnemonic list against a hand-written
`kReachableOpcodes[]` static array built from `triage-results.md`. That
triage never examined roughly 40 opcodes at all (neither confirming them
live nor dead), so the guard silently had no opinion on them. A follow-up
audit found 7 of those 40 were in fact live and reachable (`vumatrix`,
`vustring`, `movess`, plus others) — meaning the coverage guard itself had a
blind spot of exactly the kind it was built to catch.

**Fix**: replaced the hand-maintained reachable-set list with a **computed
set** — `kAllOpcodeMnemonics[]` (the full, generated 95-mnemonic list) minus
`kDeadOpcodes[]` (a short, explicitly-justified list of opcodes confirmed
unreachable, each with an inline comment citing the evidence), computed at
test-run time in `test_opcode_coverage.cpp`. This makes "opcode is live but
absent from both lists" structurally impossible — anything not explicitly
marked dead is assumed to need coverage, rather than requiring someone to
remember to add it to a reachable-list.

**Generalizable lesson**: for any completeness/coverage guard, prefer
`all − known_exceptions` (fails open — new items default to "must be
covered") over a hand-maintained inclusion list (fails closed — new items
default to "not checked," silently).

## 4. "Reachable per static analysis" and "reachable in practice" are different claims — always confirm with the shader that actually exercises the path

**What happened**: `gather_named_probe.sl`'s `sampleCone` argument
(`PI * 0.5`) is a compile-time-uniform expression. Reading the shader source
directly confirmed `CUniformLiftingPass` promotes it to single-element
uniform storage — this is what makes the crash fix (stride-threading through
`op_gatherHeader`) genuinely load-bearing rather than incidental. It would
have been easy to assume the fix was correct from code review alone; reading
the actual triggering shader source was what confirmed the uniform-lifting
path was truly exercised, not just theoretically possible.

**Generalizable lesson**: when a fix targets a specific compiler-pass
interaction (uniform lifting, constant folding, CSE), verify the test
shader actually exercises that pass by reading its source, not just by
trusting the test's name or its presence in the suite.

## 5. Three name mismatches were hiding behind what looked like one case-fold bug

**What happened** (Phase 2/T005): the `gatherHeader`/`gatherhdr` mismatch
initially looked like a single lowercase-vs-mixed-case typo. On closer
inspection it was **three separate** mismatches: `gatherElse`/`gatherEnd`
(the real mnemonics have a capital E) vs. `irBuilder.cpp`'s lowercase
`gatherelse`/`gatherend`, plus `gatherHeader` vs. an entirely different
token spelling, `gatherhdr` — not a case difference at all, a different
word. Fixing only the first mismatch found would have left the construct
still broken.

**Generalizable lesson**: when a name-mismatch bug is found, grep for *all*
occurrences of the construct's name family across the tokenizer, IR
builder, and emitter before declaring the fix complete — don't stop at the
first mismatch that explains the symptom.

## 6. `ctransform` was silently *wrong*, not silently *dropped* — a distinct failure class from `cfrom`/`mfrom`

**What happened** (Phase 5/US1): `cfrom`/`mfrom` fell into the emitter's
`if/else if` chain with no matching case and no final `else` — the
assignment was dropped with zero emitted IR and zero diagnostics.
`ctransform`, by contrast, *did* match a case — it was misrouted into the
`pfrom` family and called `op_pfrom`, a homogeneous 4×4 point-matrix
transform, when it should have called a colorspace-conversion function.
This produces plausible-looking but numerically wrong output (a
geometrically transformed color, not a colorspace-converted one) with no
crash and no diagnostic — arguably harder to catch in review than a dropped
write, since the shader visibly "does something."

**Generalizable lesson**: when auditing a long dispatch chain for coverage
gaps, don't only look for *missing* cases — also check that each *present*
case actually calls the function that matches its opcode's documented
semantics, not a same-shaped-but-different function that happens to compile
cleanly against the same call signature.

## 7. Documentation had drifted from what the code actually does, undetected until this branch's direct verification

Two confirmed inaccuracies in `DEVNOTES_DETAILS/OSHADER_UPDATES.md`
(and, by extension, `CLAUDE.md` gotcha #3, which cites the same claims):

- The claim "Unrecognised opcodes emit a once-per-shader-per-opcode warning;
  the instruction is skipped" is **false** — confirmed by direct grep of
  `llvmEmitter.cpp`: no such warning mechanism exists. Unrecognized opcodes
  are silently skipped with zero diagnostics, which is precisely the root
  cause of this entire branch's motivating bug (`cfrom`).
- The reference to `jitSymbolRetain.cpp` as the mechanism preventing macOS
  `ld` from dead-stripping `op_*`/`rsl_*` symbols is **false** — that file
  does not exist in the repository. The real (working) mechanism is
  `CLLVMJitEngine::addProcessSymbol()`, which is defined but currently has
  zero callers; the existing `.slo` tests actually resolve their symbols via
  `DynamicLibrarySearchGenerator::GetForCurrentProcess()` alone.

**Generalizable lesson**: documentation describing "what the code currently
does" (as opposed to "what it's designed to do") rots silently and doesn't
surface as a build or test failure — it only surfaces when someone reads the
actual source side-by-side with the doc. Worth periodically re-verifying
doc claims that describe implementation mechanics (not just API contracts)
against the current source, especially in files that get cited as
onboarding/gotcha references (`CLAUDE.md`).

## 8. `numVerts` can exceed `numRealVertices` — a correctness trap specific to raytrace-derivative shading

**What happened** (Phase 7/T037 gather CFG design): the JIT arg `numVerts`
can be up to 3x `currentShadingState->numRealVertices` when shading under
raytrace-derivative evaluation. A first-draft design for `gatherElse`/
`gatherEnd` considered literally reusing the existing `op_else_update`/
`op_endif_update` wrappers verbatim (since `gather`'s control-flow shape
looks structurally identical to `if`/`else`/`endif`). That would have been
wrong — those existing wrappers are bound to `numRealVertices`, and reusing
them unmodified for `gather` would silently under- or over-iterate on
raytrace-derivative batches. The design was corrected to require new
`numRealVertices`-bound wrapper functions specific to `gather`, rather than
reusing the `if`-family wrappers.

**Generalizable lesson**: two RSL constructs with visually identical
control-flow shape (both compile to a header/else/end triple) are not
necessarily safe to share JIT scaffolding — check whether either side has a
hidden batch-size assumption (like `numVerts` vs. `numRealVertices`) before
assuming structural similarity implies implementation reuse is safe.

## 9. Resolved: the interpreter does NOT share the uniform-lifted gather-operand defect — a structural compiler-level guard closes it

**The question** (Phase 7a, T041a-c): the JIT-side `gather()` crash the
T037/T038 fix guarded against was a `CUniformLiftingPass`-promoted
single-element allocation being walked with a non-zero stride across a
multi-vertex batch. Because `.rslo` is an independently-implemented
interpreter for the same opcode family, it was not obviously immune to the
identical mechanism, and needed its own repro-first investigation before
any interpreter change could even be considered (FR-009).

**First repro attempt was invalid, and a clean ASAN run was a false signal.**
The initial T041a/b repro (`gather_named_probe.sl`, `sampleCone` argument
`PI * 0.5`) ran clean under AddressSanitizer. That result was initially
treated as evidence of no defect, but static tracing found two problems with
it before it was written up:
1. `PI` parses directly to a `CConstantTerminalExpression` (`rslo.y`'s
   `SL_FCN_PI` production) — `PI * 0.5` is a pure compile-time-constant
   expression, so it never exercises `CUniformLiftingPass`'s local-variable
   promotion at all; it's a different storage class entirely
   (`SL_IMMEDIATE_OPERAND`/`currentShader->constantEntries`). The repro
   didn't test the suspected mechanism.
2. Even if it had, all of a shader instance's local variables are carved
   from a single pooled `ralloc()` block via pointer arithmetic
   (`CProgrammableShaderInstance::prepare()`, `shader.cpp:630-690`), not
   separate heap allocations. An overread that walks a few floats past a
   1-element uniform slot into a neighboring variable's bytes stays inside
   the pool's real heap bounds — ASAN's redzone instrumentation would not
   fire even if the defect were real; it would just silently read the wrong
   variable's memory. A clean ASAN run against this repro proved nothing
   either way.

**Corrected repro and the actual finding.** A second repro
(`gather_named_probe2.sl`) forced genuine `CUniformLiftingPass` promotion by
using `uniform float cone = coneA * coneB;` (product of two `uniform float`
shader parameters — not foldable to a literal, since parameter values are
symbolic at compile time) as the `sampleCone` argument to `gather()`.
Compiling this with plain `oshader` (`.rslo` text output) and reading the
emitted bytecode directly answered the question with no render/ASAN run
needed:

```
mulff  cone coneA coneB
vustring  temporary_1 "illuminance"
vufloat  temporary_2 cone
gatherHeader ... temporary_1 P Nn temporary_2 samples ...
```

`cone` (the uniform-classified local, 1-element storage per
`CProgrammableShaderInstance::prepare()`) is **never passed directly** to
`gatherHeader`. The compiler inserts an explicit `vufloat` broadcast-copy
into a fresh **varying**-classified temporary (`temporary_2`, properly
`numVertices`-scaled storage) first, and `gatherHeader` operates on that
temporary. `op_vufloat` (`rslOps.cpp:363`) confirms the copy's shape:
`dst[0] = val` with `OPERANDS2EXPR_UPDATE(1, 0)` — the varying destination
pointer advances every iteration, the uniform source is read once and
reused, never advanced. This is a general mechanism, not gather-specific:
`getContainer()` (`expression.cpp:57-145`, three overloads) is the
compiler's generic "uniform value entering a varying-typed destination"
coercion, invoked wherever codegen binds an argument/assignment whose
target context is varying but whose source expression is uniform —
`gather()`'s argument binding is just one of many call sites.

**Conclusion**: no defect exists in the `.rslo` interpreter. The suspected
mechanism (uniform single-element storage walked by a stride-advancing
varying-loop pointer) cannot occur for interpreter-compiled code, because
the compiler frontend never lets a uniform-storage pointer reach an operand
slot that a non-uniform instruction's dispatch loop will advance — it
always coerces through a `vu*`-copy into fresh varying storage first. This
is a structural, general-purpose guard (`getContainer`), not a
gather-specific patch, so it also forecloses the equivalent risk for other
builtin calls that mix uniform and varying arguments. This is why the JIT
path needed its own explicit fix (T037/T038): the JIT emitter had no
equivalent automatic uniform→varying coercion pass at argument-binding
time, so the burden fell on the gather-specific wrapper code instead — a
real, now-understood asymmetry between the two backends, not a coincidence
of what got tested. No interpreter change is needed or was made.

**Generalizable lesson**: a memory-safety tool coming back clean is not
evidence of absence when the allocator is a pooled/arena allocator — always
check the allocation strategy before trusting an ASAN/valgrind-clean result
as a safety proof, especially in codebases (like this one) that use
`ralloc`-style per-instance pooling. Separately: when a suspected defect
depends on a specific compiler-classification path being exercised (here,
`CUniformLiftingPass`-promoted local vs. constant-folded immediate),
*verify the repro exercises that exact path* before trusting its result —
inspecting the compiled bytecode directly (`oshader` without `--jit`, which
emits human-readable `.rslo` text) is cheaper and more conclusive than a
runtime/ASAN run, and was the discriminating check here.

**Dynamic ASAN confirmation (added 2026-08-21, at explicit user request).**
The bytecode-level finding above was treated as sufficient to close T041c,
but the user did not accept static analysis alone as a substitute for the
empirical ASAN check the original T041a-c methodology called for — a
reasonable position: the bytecode reading is a strong argument, not a
direct observation of runtime memory behavior. Both repros were run under
`build-asan/src/orender/orender` (a separate, interpreter-only ASAN build
tree — no LLVM/JIT support, confirmed via `asan_configure.log`) with
`ASAN_OPTIONS=detect_leaks=0:halt_on_error=0`:
- `repro-gather-interp-raytrace.rib` (`gather_named_probe`, the original,
  non-exercising `PI * 0.5` repro — run because the user named it
  explicitly, even though it was already known not to test the suspected
  path).
- `repro-gather-interp-raytrace2.rib` (`gather_named_probe2`, the corrected
  repro that genuinely exercises `CUniformLiftingPass` promotion of the
  gather-bound uniform).

Both completed successfully with valid, correctly-sized TIF output; neither
log contained any ASAN report (no heap-buffer-overflow, no
use-after-free, nothing implicating `GATHERHEADEREXPR_UPDATE` or
`operand()`'s handling of `sampleCone`). This confirms — dynamically, not
just structurally — that the interpreter path is clean. One methodological
note worth keeping: `Display` output filenames in a RIB are CWD-relative,
not RIB-file-relative — running orender from a different working directory
than the `.rib` writes the `.tif` next to wherever the process was
launched from, not next to the RIB, which is easy to mistake for a failed
render on first glance.

**Lesson**: when an investigation's task description specifies a particular
empirical method (ASAN, valgrind, debug logging), execute that method —
don't substitute a different, even structurally stronger, form of evidence
without checking with the user first. Static and dynamic evidence answer
different questions ("can this happen by construction" vs. "did this happen
on this run"), and a careful-change discipline like this project's FR-009
benefits from having both on record before closing a defect investigation.
