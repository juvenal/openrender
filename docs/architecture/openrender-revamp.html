openRender · architecture brief · 6 November 2026

One renderer, ten clean domains.

openRender is a RenderMan-compliant renderer with a twenty-year Pixie lineage. Its revamp splits a tightly knotted codebase into independent, swappable parts. The goal is a modern, physically based renderer that still renders every classic RenderMan scene the way it always has.

Before · early October 2026, before spec 021

A hub and a knot

One central object held the renderer's state, and every part read and wrote it. Hiders, which decide what is visible, were the same class as the shading engine, which decides what it looks like. Nothing in the build stopped a new shortcut from being added.

Now · master, 6 November 2026

Hiders and shading apart, the core next

Half the boundary work is done. The parser, the graphics state, texturing, displays and plug-ins stand on their own, and shading is now a self-contained library that reaches the renderer only through one versioned interface. Spec 029 cut the knot between hiders and shading: each hider now owns a shading context instead of being one. What remains is the direct reads of the renderer core from the hiders and geometry, which specs 030 and 031 take on.

Target · after the full roadmap, 022–057

Ten domains, one composition root

Every part depends only on what the constitution allows. Visibility, shading and light transport become three independent choices. Integrators get a new tenth domain, Transport. The core only assembles the parts and owns no behavior of its own.

Planned architecture, not delivered. It covers the full roadmap, specs 022–057. Spec 042 is the PBR milestone, and 049–050 (OSL, path tracer) end the critical path. Specs 041–057 are provisional until each is specified.

The final goal

Pick what you see, how it looks and how light moves, independently

Today, a RenderMan surface shader computes its own lighting. That model is kept as the classic integrator, and under it every existing scene renders exactly as it does now.

Next to it the revamp adds physically based transport. The renderer integrates the light, materials are described as closures, and lights can be sampled by area. Neither model needs a different hider or a different shading language.

The commitment that holds this together: every hider × integrator × material combination either renders or stops with a clear diagnostic. Nothing degrades silently. A dedicated compatibility suite checks every one of those combinations.

Risks and pitfalls

What could slow it down, and the guard against each

These risks come from the project's own records: the violation registry, the bug tracker, and lessons learned while delivering the specs so far.

High

The hiders still lean on the core

556 references and 164 allowlist lines remain. Another 78 lines are link-time substitution pairs that only fail at run time.

GuardEach remaining violation has a scheduled owner: the registry in 030 and the geometry interfaces in 031. The build check alerts on any increase.

Medium

A long, strictly ordered critical path

Eight stops remain on the road to the path tracer, and each one depends on the stop before. A slip early on, especially in 030, pushes back everything after it.

GuardTwo items in flight at once. The off-path specs (031, 032, 034, 043, 048) fill idle capacity, and each spec is a mergeable slice that delivers value alone.

Medium

Specs that pass alone can break together

Specs 029 and 038 each passed on their own. Together, a static program lost its renderer, because 038 removed a reference that the link had reached it through by accident.

GuardEach spec is checked again on the merged tree, on both platforms, before it reaches master. That run caught this one, and the link tests now assert that a renderer registered.

Medium

An unexplained crash in point-cloud lookups

One texture3d/bake3d scene segfaults now and then on Linux under load, on master too (#122). Its cause is not established yet.

GuardFiled at the top priority with backtraces and failure rates. The next step is a thread-sanitizer or symbolized run of the point-cloud code.

Medium

Interpreter and JIT can disagree

The same shader can still give different results in its two forms. One known case runs a guarded uniform assignment regardless of its condition (#8). Another affects light message passing (#115).

GuardParity suites run every shader both ways. Native JIT lowering (055) waits until #8 is fixed.

Medium

Bit-exact output is fragile

Regrouping one expression, or letting compilers fuse multiply-adds differently, changes the last bit of an image. A tidy refactor can look like a regression.

GuardEach call site keeps its exact arithmetic, and recorded replays catch any drift. A red replay means code moved; it is never a reason to widen a tolerance.

Medium

OSL brings heavy dependencies

OpenImageIO 3, an LLVM 18 floor and CMake 3.23 come with it, and the legacy image codecs are removed. Building LLVM from source takes nearly two hours.

GuardOpenImageIO lands first as an optional backend (048). A hands-on spike precedes the OSL backend, and vcpkg caches the vendored toolchain.

Watch

Some images will change on purpose

A direct integrator cannot reproduce full global transport. Correct volume shading also changes how CSG interiors look today.

GuardLike is compared with like. Each intended change gets a documented re-render, and the classic default stays identical.

Watch

The boundary check runs in CI only on release tags

Between releases it relies on discipline: the check runs locally before every review.

GuardEvery phase report includes a passing architecture run. Running it in CI on every push is a cheap step that remains open.
